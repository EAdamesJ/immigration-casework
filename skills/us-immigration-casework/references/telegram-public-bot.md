# Ruta Consular public Telegram bot

`scripts/telegram_bot.py` is an optional working long-polling Telegram Bot API service. It needs a user-owned bot token and an always-running host. Installing this skill neither creates a Telegram identity nor launches the service. The repository's `integrations/telegram/` contains deployment instructions, command menu, privacy-policy template and profile art. No live bot/token/server is bundled.

The public service accepts anyone who starts a private conversation, up to a configured capacity. Group/channel updates, bots and sender/chat mismatches are ignored. Every task/reminder/practice state is scoped to that private chat ID; knowing another person's task number is not authorization. The operator is responsible for real deployment access controls, encryption, backups, identity checks and applicable policies. Do not call public availability a guarantee of unlimited capacity, load testing, privileged representation or professional legal service.

Commands cover start/help, personal tasks, task completion, timezone, opt-in reminders, guided B1/B2 or immigrant interview practice, DS-260/document guidance, private ID, privacy and deletion. The menu is registered by the explicit setup command through setMyCommands and setChatMenuButton; reply-keyboard buttons are included in bot replies. Name/description/photo can be configured by setup when a valid token is locally available. BotFather creation/credential changes remain with the user. Never paste tokens into chat or commit them. If a token was shared, recommend rotating it through BotFather before public activation.

The default bot uses deterministic questions and bounded organizational commands, not a generative LLM. Practice advances one question at a time with general clarity/consistency reminders; it does not analyze factual correctness, assess approval odds or save the answers in its database. Telegram still processes/stores the conversation according to its own terms. DS-260/document commands give guidance and route work to the private skill; they do not fill a full application within Telegram or collect CEAC credentials. Incoming documents/photos/voice are not downloaded. Never claim Telegram bot chats are end-to-end encrypted or confidential legal files.

Tasks must have short neutral titles; the helper blocks selected common identifier patterns, not all personal data. No real source documents should be sent to the bot. Reminder creation requires an explicit timezone and /avisos activar; timestamps have explicit offsets and must match the chosen IANA zone. Reminders are personal targets within 90 days, not calculated legal deadlines or automatic case/visa-bulletin monitoring. The worker must be running; delayed/offline reminders older than one day are dropped rather than sending a stale batch. /avisos desactivar cancels pending reminders; an in-flight send may still complete. Never promise guaranteed delivery.

SQLite commits update deduplication, task mutations, offset and reply enqueue together. Replies/reminders are marked dispatching before the network call. An unknown network result is held unknown rather than automatically resent; only an explicit Telegram 429 response is retried after its retry_after. Restart treats unresolved dispatching entries as unknown. Accepted sends are removed, and unknown outbox/update history is purged after seven days. Users inactive for 90 days are removed. /borrar confirmar deletes user state, tasks, reminders, binding and old queued messages; a final confirmation temporarily retains the chat ID until its send/retention cleanup. Telegram history and operator backups require separate deletion. Database storage is plaintext with restricted local permissions, not application-level encryption.

Use one worker per token/database, with persistent disk. Public deployment requires a real operator contact and HTTPS privacy policy in environment configuration. Never add a real token to examples, logs, CI or issue reports. The API client uses fixed api.telegram.org HTTPS, no redirect following and sanitized errors. Operator status returns aggregate counts only. The default service has quotas/rate limits but is not a distributed/high-availability SaaS. A large public launch requires measured capacity, operational monitoring, a recovery plan and appropriate data handling.

Optional v2.0 ledger binding is operator-only: verify the actual person's identity/case authority out of band; obtain authorization for the exact chat/case scope and record verification_ref. The user must already have started the bot. `link` checks the actor is a case member. /pendientes then reads task IDs/status for that actor, or the case owner, without copying review notes, files or task titles from the case. Removing the member blocks subsequent reads. Chat IDs are identifiers, not proof of identity. Users cannot bind an arbitrary case through a chat command. /borrar removes the binding. No ledger mutation or professional invitation is performed through the bot.

Before claiming live integration, actually confirm BotFather identity, configured commands/photo, running host, private multi-user isolation, opt-in reminder delivery and server data lifecycle using synthetic accounts. The automated suite uses transport stubs and does not activate a public Telegram bot. Keep code-ready/configured/running distinctions explicit in the user-facing result.

Technical baseline checked 2026-10-31: [Telegram Bot API](https://core.telegram.org/bots/api), [Telegram Bot Features](https://core.telegram.org/bots/features). Long polling and webhooks cannot be used simultaneously. This implementation refuses an active webhook instead of deleting it silently; switch an existing integration only with specific authorization. The operator accepts and follows Telegram's current bot terms directly.
