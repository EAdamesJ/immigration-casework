# Professional collaboration and review

Use a private local coordination ledger to assign work, preserve artifact versions and record independent review. This is a workflow record for a trusted operator or an authenticated host application; it is not a multiuser web app, authentication server, access-control boundary, encrypted vault or proof of professional licensure. Anyone with filesystem write access can change the ledger. Never present its roles as security isolation or attorney-client privilege. Real shared folders/accounts require the provider's own access controls, consent and professional obligations.

Establish case authority and a minimum participant directory outside this public skill: actual person, contact, consent, role, representation scope and how professional credentials were checked when relevant. An `actor` ID is an attestation by the host, not a login. Do not infer that a reviewer is licensed because they have that role. Before sending anything, identify the recipient and the exact case/data scope using trusted records. Do not place real clients in GitHub issues, shared sample calendars or public demonstrations.

Roles apply per case: owner creates the case, assigns/removes non-owner members and assigns independent reviews; preparer edits artifacts and prepares actions; reviewer decides only the review actually assigned to them; observer has no mutation rights except tasks explicitly assigned to them. A member from one case cannot operate on another through these workflow APIs. This is logical scoping, not filesystem-level tenant isolation. Revoking a member locally blocks future workflow mutations and unassigns active reviews/blocks unfinished tasks; it does not revoke Drive, mailbox, calendar or shared-file access.

Artifact flow: compute SHA-256 from the actual reviewed file; `artifact.revise` appends a new version and starts it as draft. `review.assign` binds an independent reviewer to the current revision/hash. `review.decide` records approved or changes_requested and a review note. The author cannot review their own work. Any new content hash creates a new draft with no approval; old versions/feedback remain in history. “Approved” is a professional workflow attestation, not an electronic signature, legal certification, filing or immigration approval. Verify the file hash again before export/sharing. The code records a provided hash and does not inspect the referenced file automatically.

Tasks have assignee, neutral summary and todo/in_progress/blocked/done status. Only owner or assignee changes a task. Put sensitive substantive comments in the protected case record; ledger snapshots may contain review notes and external destinations, so treat them as private. Use the v1.2 curated package exporter for the actual handoff: case chronology, verified facts, uncertainties, questions, notice deadlines, evidence index, current document hashes and source ledger. Do not dump the whole coordination database into a professional packet.

Every mutation includes the latest expected_revision. The SQLite transaction serializes writes and rejects stale revisions. Reread and reconcile when another operator updated the ledger; do not overwrite or auto-merge professional judgments. Do not place a live SQLite database on an untested network sync drive for concurrent editing. Use a single controlled host process or implement a proper authenticated server for distributed teams.

An append-only-through-the-API SHA-256 audit chain records actor, operation, time, input digest and resulting state digest. Verification detects missing/reordered/edited entries or snapshot mismatch. It is not externally anchored, signed, immutable or tamper-proof against a person who can rewrite the database and chain. Keep backups and independent provider receipts. Reject a damaged ledger rather than silently repairing history. Store outside Git; POSIX folder/file permissions are restricted, Windows ACLs and encryption remain host responsibilities.

Installing v2.0 does not invite colleagues, change folder permissions, send mail or create reminders. Prepare concrete recipient/content/data disclosures before required host authorization, preserving clearly applicable prior instructions. Do not ask permission solely to prepare a local reviewable package.
